- **What**: **Engine bug (upstream, ironhold-lib)** — any scene whose active camera is a `"flycam"`-tagged prefab (legacy tag or explicit `camera_mode: Flycam((...))`, tried both) never renders `kind: Prop`/`Actor` GLB meshes. Only `kind: Primitive` geometry (e.g. the `"ground"` cuboid) renders; GLTF models (aliens, columns, decals in `showcase.scene.ron`) stay fully invisible even at point-blank camera distance, after 20+ second waits, and regardless of camera movement/rotation (all independently confirmed working via the on-screen position readout and pitch changes). Reproduced identically on the pre-existing, unmodified `showcase.scene.ron` — not caused by anything in this session. Root cause not found in `crates/ironhold_core/src/capabilities/flycam.rs` (pure camera-movement code, no rendering/visibility logic) — likely elsewhere in the GLTF-scene spawn or camera-target visibility path. Checked every bundled ironhold-lib example project (`camera_modes`, `custom_materials`, `terrain_demo`) that uses `"flycam"` or `camera_mode: Flycam` — **none combine it with a real GLB Prop model**, so this exact combination appears untested by the engine's own example/screenshot-baseline suite, which is probably why it's gone unnoticed. **Confirmed workaround**: a `"player"`-tagged prefab (movement zeroed) with `camera_mode: Fixed((position: ..., look_at: ..., fov: ...))` renders GLB Props correctly — used for `showcase_camera`/`menu_camera` in `prefabs/prefabs.ron` to fix `showcase.scene.ron` and the new `start_menu.scene.ron`. Free-fly exploration of `showcase.scene.ron` was lost as a result (it's now a single static angled view instead of a flyable tour) — worth restoring once the upstream bug is fixed.
- **Why**: Worth filing against `ironhold-lib` with this repro (any GLB Prop + `"flycam"`/`camera_mode: Flycam` combination) since it silently breaks any scene design that wants a free-fly camera over real 3D content, not just primitives.
- **While**: Implementing the start menu (`start_menu.scene.ron`) and giving it a decorative GLB backdrop — the backdrop rendered as an empty gradient until this was diagnosed and worked around.
- **Update (still open)**: Re-tested against `ironhold-lib` commit `452e2e20f54b` (2026-08-24) — updated via `update_lib.py` after being told this batch shipped a flycam fix. It did not fix this bug: `showcase.scene.ron` with `prefab: "flycam"` still renders zero GLB Props on this build (re-confirmed empirically, screenshot identical to before the update). Reading the updated `docs/20_data_formats.md`, that batch's flycam fixes were three different, unrelated issues — a flycam prefab's own body-defining fields never rendering (expected, camera-only), duplicate-flycam-tag spawn priority, and player+flycam camera-priority when both are present in one scene — none of which describe our symptom (other, unrelated GLB Props elsewhere in the scene going invisible while viewed through a flycam). The `showcase_camera`/`menu_camera` Fixed-camera workaround is still required; keep it until a fix that actually addresses "GLB Props invisible under a flycam view" lands.
